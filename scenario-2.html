シナリオ 2

コード自動レビューシステム構築

Claude Codeを活用したCI/CDパイプラインへのAIレビュー統合

D3 Claude Code (20%) D1 エージェント設計 (27%)

シナリオ概要

このシナリオでは、開発チームのコードレビュープロセスにAIを組み込むプロジェクトが舞台です。プルリクエスト（Pull Request: コードの変更を提案する仕組み）が作成されたときに、AIが自動的にコードをレビューし、改善点を指摘するシステムを構築します。

具体的には、以下のような業務場面が設定されます。

  • GitHub上のプルリクエストに対してClaude Codeが自動レビューコメントを付ける
  • CI/CDパイプライン（コードの自動テスト・デプロイの仕組み）へのAI統合
  • セキュリティ脆弱性の自動検出
  • コーディング規約（Coding Standards）への準拠チェック
シナリオの背景

コード自動レビューは、Claude Codeのヘッドレスモード（--printフラグ）を活用する代表的なユースケースです。人間の対話なしにCIパイプラインからClaude Codeを呼び出し、レビュー結果を自動的に返す仕組みが問われます。

関連ドメインと出題傾向

D3: Claude Codeの設定とワークフロー（Claude Code Configuration & Workflows）

試験配点の20%を占めるドメインです。Claude Codeの各種機能と設定方法が問われます。

  • ヘッドレスモード（--print / -p）― CI/CDでの非対話実行
  • CLAUDE.md ― プロジェクト固有のルールやコーディング規約をAIに伝える設定ファイル
  • Hooks（フック）― ツール実行の前後にカスタム処理を挟む仕組み
  • 権限制御 ― deny/ask/allowの3段階と評価順序
  • セキュリティアーキテクチャ ― サンドボックス、データ保護

D1: エージェント型アーキテクチャとオーケストレーション

レビューシステム全体のアーキテクチャ設計が問われます。

  • サブエージェント活用 ― コード分析、テスト生成、ドキュメントチェック等の専門エージェント
  • コンテキスト隔離 ― 各レビュータスクが互いに影響しない設計
  • 暴走防止 ― --max-turnsや--max-budget-usdによるコスト・実行回数制限

対策ポイント

対策1: Claude Codeの2つの使い方を区別する

対話モード（開発者が手元で使う）とヘッドレスモード（CI/CDから自動実行する）の違いを明確に理解しましょう。試験では「CI/CDでどちらを使うべきか」が問われます。ヘッドレスモードには--printフラグとANTHROPIC_API_KEY環境変数が必要です。

対策2: Hooksの仕組みを理解する

Hooksは「ツール実行の前後に自動的に走るスクリプト」です。PreToolUseでコマンドをブロックするには、stderrにメッセージを出力して非ゼロの終了コードで終了します。stdoutはツール結果の変更用なので混同しないようにしましょう。

対策3: 権限制御の評価順序を暗記する

Claude Codeの権限はdeny → ask → allowの順で評価されます。denyが常に最優先で、明示的に拒否されたツール操作は他の設定で上書きできません。この評価順は安全性を最優先にする設計思想に基づいています。

対策4: セキュリティの多層防御を意識する

bypassPermissionsモードはコンテナなどの隔離環境でのみ使用すべきです。本番環境のCIで無制限に実行するのは危険です。--max-turnsや--max-budget-usdを組み合わせた多層防御が推奨されます。

よくある誤解

「CLAUDE.mdに書けばClaude Codeが自動でCIを実行してくれる」と誤解しがちですが、CLAUDE.mdはあくまで指示書（ルールブック）です。CI実行の自動トリガーにはCI/CDツール側の設定が必要です。

練習問題

Q1. 開発チームがGitHub Actionsのパイプラインにコード自動レビュー機能を追加しようとしています。プルリクエスト作成時にClaude Codeが自動でレビューを実行し、結果をコメントとして投稿する設計です。この場合、Claude Codeをどのように起動すべきですか？
A) claude --print フラグで起動し、ANTHROPIC_API_KEYを環境変数に設定する
B) claude を対話モードで起動し、スクリプトでキー入力を自動化する
C) CLAUDE.mdにCI実行トリガーを定義し、Claude Codeに自動起動させる
D) Claude APIのMessages APIを直接呼び出し、Claude Codeは使用しない
CI/CDパイプラインでClaude Codeを使うには、--print（または -p）フラグによるヘッドレスモードで起動します（A）。対話モードはCIには不向きで、CLAUDE.mdはあくまで指示書であってトリガーではありません。Messages APIを直接呼ぶ方法はClaude Codeのファイルアクセスやツール機能を活用できず、コードレビューには非効率です。
Q2. コードレビューの自動化において、Claude Codeが意図せず本番データベースへの接続コマンドを実行してしまうリスクが懸念されています。このリスクを最小化するために最も適切な対策はどれですか？
A) CLAUDE.mdに「本番データベースに接続しないこと」と記載する
B) --max-turns=1を設定して、1回のツール実行で強制終了させる
C) permissions.denyで危険なコマンドを明示的にブロックし、隔離環境で実行する
D) 対話モードで実行し、各コマンドの実行前に人間が確認する
permissions.denyで危険なコマンドを明示的にブロックし、さらにコンテナなどの隔離環境で実行する多層防御アプローチが最適です（C）。CLAUDE.mdへの記載（A）はプロンプトレベルの対策であり確実ではありません。--max-turns=1（B）はレビューに複数ステップ必要な場合に機能しません。対話モード（D）はCI/CDの自動化と矛盾します。
Q3. コードレビューのCIパイプラインで、Claude Codeのフック（Hooks）を使って「特定のファイルパターン（.envファイルなど）への書き込みをブロックする」機能を実装しようとしています。PreToolUseフックでコマンドをブロックする正しい方法はどれですか？
A) stdoutに「BLOCKED」と出力し、終了コード0で終了する
B) stderrにフィードバックメッセージを出力し、非ゼロの終了コードで終了する
C) stdoutにJSON形式のエラーオブジェクトを出力し、終了コード1で終了する
D) 環境変数CLAUDE_BLOCK=trueを設定し、終了コード0で終了する
PreToolUseフックでブロックするには、stderrにフィードバックメッセージを出力し、非ゼロの終了コードで終了します（B）。非ゼロの終了コードがブロックのシグナルであり、stderrの内容がClaude Codeへのフィードバックとして渡されます。stdoutはツール結果の変更用に予約されているため、フィードバックにはstderrを使う必要があります。
