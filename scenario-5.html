シナリオ 5

API統合データパイプライン

外部API連携の大規模データ処理とレート制限対策

D2 ツール設計 (18%) D5 コンテキスト管理 (15%)

シナリオ概要

このシナリオでは、外部APIと連携して大量のデータを処理するパイプラインを構築するプロジェクトが舞台です。たとえば、顧客データベースから数千件のレコードを取得し、Claude APIを使って分類・要約・分析する処理を自動化するシステムを設計します。

具体的には、以下のような業務場面が設定されます。

  • 大量のデータを Claude API で処理する際のレート制限（Rate Limits）対策
  • Message Batches API を使ったコスト効率の良い一括処理
  • 外部APIとの連携時のエラーハンドリングとリトライ戦略
  • 処理進捗のモニタリングとアラート設計
シナリオの背景

APIを使った大規模データ処理では、「一度にどれだけ送れるか」「エラーが起きたらどうするか」「コストをどう最適化するか」という運用面の設計力が問われます。技術的な知識だけでなく、現実のシステム制約（レート制限やコスト）を考慮した設計ができるかが鍵です。

関連ドメインと出題傾向

D2: ツール設計とMCP統合

試験配点18%。外部APIをツールとして組み込む設計が問われます。

  • 外部APIのツール定義 ― パラメータ設計、レスポンス処理
  • Message Batches API ― 大量リクエストの非同期一括処理（通常の50%のコスト）
  • サービスティア（Service Tiers）― Standard / Priority / Batch の3段階
  • エラーハンドリング ― HTTP 429（レート制限）、5xx（サーバーエラー）への対応

D5: コンテキスト管理と信頼性

試験配点15%。大規模処理の信頼性とモニタリングが問われます。

  • レート制限（Rate Limits）― Token Bucket方式、キャッシュ非カウント、ティア別制限
  • トークン管理 ― 入力・出力のトークン消費最適化
  • データプライバシー ― Consumer / Commercial / ゼロ保持の3区分
  • モニタリング ― 処理成功率、エラー率、コストの追跡

対策ポイント

対策1: 3つのサービスティアを区別する

Standardは通常のAPI呼び出し。Priorityは高優先度（追加料金）。Batchは非同期一括処理で50%コスト削減。試験では「数千件のデータ分類を最もコスト効率よく処理するにはどのティアを使うか？」のような問題が出ます。答えはBatchです。

対策2: レート制限対策のベストプラクティスを覚える

HTTP 429エラー（レート制限）への対策は指数バックオフ（Exponential Backoff）が基本です。さらに、プロンプトキャッシングを活用するとキャッシュヒット分はレート制限にカウントされないため、実質的な処理能力を向上できます。

対策3: Batches APIの特性を理解する

Batches APIはリアルタイム応答が不要な大量処理に使います。50%のコスト削減は大きなメリットですが、処理完了まで最大24時間かかる可能性があります。「即座に結果が必要」な場面には使えません。

対策4: モデル選択とコスト最適化を考える

大量の単純な分類タスクにはClaude Haiku（高速・低コスト）が最適です。すべてのタスクに最高性能のOpusを使うのはコスト的に非効率です。タスクの複雑さに応じてモデルを選択する考え方が試験で問われます。

よくある誤解

「レート制限に引っかかったら待てばいい」と単純に考えがちですが、Token Bucket方式ではバケツのサイズ（上限）と補充レート（回復速度）の両方を理解する必要があります。大量リクエストを一気に送ると、バケツが空になって長時間待つことになります。

練習問題

Q1. ECサイトのカスタマーレビュー5,000件を「ポジティブ」「ネガティブ」「ニュートラル」に分類するプロジェクトがあります。即時の結果は不要で、翌日までに完了すればよいとします。最もコスト効率の良いアプローチはどれですか？
A) Claude Opusを使ってStandard APIで1件ずつ処理する
B) Claude Haikuを使ってMessage Batches APIで一括処理する
C) Claude Sonnetを使ってPriority APIで高速処理する
D) Claude Haikuを使ってStandard APIで並列処理する
最もコスト効率が良いのは、最も安価なモデル（Haiku）と最も安いティア（Batches API: 50%割引）の組み合わせです（B）。単純な分類タスクにOpus（A）はオーバースペック、Priority（C）は追加料金がかかり不要、Standard並列（D）はBatchesより高コストです。翌日でよいという条件がBatches APIの利用を可能にしています。
Q2. Claude APIのレート制限について、正しい説明はどれですか？
A) レート制限は1日あたりのリクエスト数のみで管理される
B) 一度レート制限に達すると、翌日までAPIを利用できない
C) Token Bucket方式で管理され、プロンプトキャッシュのヒット分はカウントされない
D) Batches APIにはレート制限が適用されない
Claude APIのレート制限はToken Bucket方式で管理されます（C）。バケツにトークンが一定速度で補充され、リクエストごとに消費します。重要なポイントとして、プロンプトキャッシュがヒットした場合、そのトークン分はレート制限のカウントから除外されます。1日単位（A）ではなく分単位で管理され、一時的な制限（B: 翌日まで使えないわけではない）であり、Batches APIにもレート制限は存在します（D）。
Q3. データパイプラインでClaude APIを呼び出した際にHTTP 429（Too Many Requests）エラーが返されました。リトライ戦略として最も適切なのはどれですか？
A) 指数バックオフ（Exponential Backoff）でリトライ間隔を1秒→2秒→4秒と増やしながら再試行する
B) 即座に同じリクエストを再送する
C) 10分間固定で待機してから再試行する
D) リクエストを破棄し、処理をスキップする
HTTP 429（レート制限）には指数バックオフが最適です（A）。リトライ間隔を徐々に増やすことで、レート制限の回復を待ちながら効率的にリクエストを再送できます。即座再送（B）は制限をさらに悪化させ、固定10分待機（C）は非効率、処理スキップ（D）はデータ欠損を招きます。
